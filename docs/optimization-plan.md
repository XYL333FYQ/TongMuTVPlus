# 全站排查与优化方案

> 日期：2026-10-31（北京时间）。范围：整个仓库（网页、接口、房间服务、安卓壳、桌面壳、打包与发布）。
> 做法：只看、只量、不改代码（本文件除外）。每一条都带着我实际量到或看到的证据；没有亲眼验证的，会明确写"未验证"。
> 说话方式：尽量不用术语。需要用时，括号里用大白话解释。

---

## 一、先说结论（最重要的五句话）

1. **项目最大的问题不是哪个页面丑，而是"摊子太大、没人看门"**：26 万行代码、59 个页面、257 个接口，却没有任何一个自动检查在推送前把关。推送到 main，就直接打包发布。
2. **手机上"打开慢、切页不够顺"的头号原因找到了**：每个页面一打开，都要先下载约 900KB（压缩后）的脚本，其中一半以上是只有"弹幕/繁简转换"才用得上的东西。关于页、反馈页也一样。
3. **有 190 条已知漏洞提醒**（4 条严重、96 条高危）。好消息：大半来自"没人用的依赖"和"打包工具"，删掉或升级就能消掉一大批；坏消息：Next.js 本身（你的网站框架）停在了一个已经没人维护的版本，要升级是一项大工程。
4. **安全方面有两处值得认真对待**：站长的"重置配置"是一个普通链接就能触发的操作；登录凭证放在网页脚本能读到的地方。其余部分（媒体代理防内网探测、登录限流、安装包更新校验）做得比我预期的好。
5. **海报加载是"先撞墙再换路"**：首页、片库每次打开，有 19 ～ 27 张海报先被豆瓣拒绝（HTTP 418），再改走备用镜像。慢一倍，还满屏报错。

### C. 安全

| C4   | **登录限流有（返回 429），但覆盖是否完整未验证**：登录、注册、改密码、扫码登录、第三方登录各入口是否都限流，需要逐个测。                                                                                                                                                             | 代码里看到 429，未逐接口验证                                                               | 中   |

## 三、优化方案（分五个阶段，全站）

> 原则：① 先做**不改外观、风险低、见效大**的；② 碰**禁区**的，先拿到你的明确授权；③ 每一阶段都有**验收标准**，验收不过不进下一阶段；④ 不用"砍效果"换流畅；⑤ 每阶段单独分支、单独提交，你说"推"才推。

### 阶段 0：先立规矩（约半天）——让后面的每一步都有保险

| 步骤 | 做什么                                                                                                        | 验收                                         |
| ---- | ------------------------------------------------------------------------------------------------------------- | -------------------------------------------- |
| 0.1  | 新增"推送前检查"流程：类型检查、代码检查、测试、格式；镜像打包要等它通过才开始。                              | 故意推一个有错误的分支，检查变红，镜像不打包 |
| 0.2  | 把这次的"切页基准测试"（点击 → 滑块起步 → 页面出现 → 长任务数）做成可重复的脚本放进仓库，并记下当前基线数字。 | 脚本一条命令跑出表格；基线写进 `PROGRESS.md` |
| 0.3  | Windows 打开"开发人员模式"（解决构建最后一步的符号链接权限）；记录本机偶发崩溃的复现条件。                    | `pnpm build` 一次跑到底，不再 EPERM          |
| 0.4  | 确认备份：跑一次现有的 sqlite 备份与恢复演练。                                                                | 备份文件能恢复到临时目录并能打开             |

## 五、已确认的前提（2026-10-31 用户答复）

1. **部署**：VPS + Docker。所有验证以 Docker 镜像为准。
2. **功能**：现有功能**一个都不去掉**，只改善。方案里凡是"删除/默认关闭"的说法一律作废，改为"按需加载、体检、修问题"。删的只有**确认没人引用的第三方依赖包**（它们不是功能）。
3. **禁区**：有用就可以改，但必须保证不出问题。做法：每次只动一处；改之前先补测试把现有行为"钉住"；改完跑全部测试 + 房间测试 + 浏览器手点对应流程；单独分支、单独提交，出问题能一键退回。
4. **数据库**：SQLite（已核实，见 4.4）。
5. **Next.js 升级**：见下方说明；先做"体检"，不直接动手。

**Next.js 升级是什么？** Next.js 是整个网站的"地基"（页面怎么生成、怎么切换、接口怎么跑都靠它）。你现在用的是 14 版，官方已经不再给 14 版打安全补丁，这次查出的"严重"漏洞里有 25 条就出在它身上。升级到 15（或更新）版，就是"换一个还在保修期的地基"。好处：堵掉这批漏洞，以后还能继续拿补丁。代价：新地基有些规矩变了（比如读取 Cookie、网址参数的写法），全站要跟着改一遍，改完必须把所有页面和功能回归一遍。所以计划是：先在单独分支上做"体检"，列出要改哪些地方、风险多大，给你看了再决定什么时候做。
