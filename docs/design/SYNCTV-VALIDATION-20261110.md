# SyncTV 隔离验证记录

日期：2026-11-10。目的：判断能否以 SyncTV 为本站一起看模块的基础；不是产品接入或完整验收。

## 实验环境

- 官方 SyncTV 服务端 v1.0.14 的 Linux amd64 程序及 PostgreSQL 18，运行在 WSL 2 的临时目录，本机回环监听，使用独立临时账号和测试数据库。
- SyncTV 官方多架构镜像索引 digest 为 `sha256:0f58fb9b5c91571ab4e3048679b12b4b69f68269ca4e62c3cacfaa83c5cc4934`，与 [v1.0.14 官方发布](https://github.com/synctv-org/synctv/releases/tag/v1.0.14)的 digest 文件一致；所下载程序层逐项做了 SHA-256 校验。
- 片源使用本项目已有的 13,083 字节测试 MP4，全部账号、房间、消息和数据均为本次实验创建；没有接入本站真实账号或实际片源。
- 原始脚本及结果在 `output/synctv-evaluation-20261110/`：`test-synctv.py`、`test-results.txt`、`test-restart.py`、`test-restart-results.txt`。该目录为被 Git 忽略的本地证据，不是新产品依赖。

## 实际结果

本机隔离测试结果 **28 项通过、0 项失败**；重启数据库及 SyncTV 后的检查 **5 项通过、0 项失败**。其中：

1. 两个不同测试账号加入房间，各自建立 WebSocket；房主添加测试 MP4 并开始共享播放状态，两个连接均收到相同媒体与跳转到 12 秒的事件。断开重连的成员收到最新状态。
2. 普通成员默认无权跳转；第二个连接收到聊天事件。两个连接使用同一普通房主账号时都能发送控制，说明该实验场景不强制单连接控制。
3. 账号可重新登录，测试房间、两个成员、媒体条目和聊天消息在数据库及服务重启后仍存在。
4. 旧站 Socket.IO 握手直接访问 SyncTV 返回 HTTP 404；把测试用的本站来源 ID、视频 ID 和集数直接作为 SyncTV `sourceConfig` 提交返回 HTTP 400。适配不是改个服务地址就能完成。
5. 官方服务返回 Web 首页和 Flutter 启动脚本。另在本机真实 Chrome 打开该地址，房间目录显示测试创建的两个房间；视口为 1103×783、设备像素比 1.5，所检查的控制台错误为空。登录窗要求勾选用户协议，本次未接受，未通过浏览器登录、创建房间或播放视频。

源码阅读发现，[SyncTV App v1.1.32 房间设置页](https://github.com/synctv-org/synctv-app/blob/v1.1.32/lib/features/room/presentation/room_settings_page.dart)已有选择本地图片、更新和移除房间封面；[上传服务](https://github.com/synctv-org/synctv-app/blob/v1.1.32/lib/data/synctv_api/synctv_file_upload_service.dart)有类型及大小校验。这是源码证据，不是实际上传成功证据。房间卡片在所接收的封面 URL 为空时显示占位；是否由服务端自动供应当前影片海报仍待确认。

## 结论与未覆盖范围

结果支持继续以 SyncTV 的服务端和功能实现为基础建设房间模块，本站界面须符合现有整体风格；不能据此说已经完成本站集成。仍需验证：

- 官方客户端与服务端所选版本配套关系、真实浏览器中的完整加入房间和视频解码、两个独立浏览器及手机/桌面设备同步。
- 本站账号的一对一绑定、登录、退出、禁用及权限撤销；不是所有 SyncTV 用户共用一个管理员账号。
- 本站真实 MP4/HLS 来源、剧集、字幕、请求头、过期链接、跨域和受限媒体代理。
- 本地图片上传、封面权限，以及“自定义图片 → 当前影片海报 → 占位”的展示规则。
- 旧 SQLite 房间数据向 SyncTV 数据模型迁移、旧邀请及回滚；新旧播放器的声音和生命周期协调；上线环境、备份和客户端兼容。

从本站读取的一份旧 `.env` 曾被第一次试验的 SyncTV 设置命令尝试解析并报格式错误；该尝试没有建立业务连接或更改文件。后续已将运行目录切换到隔离目录并禁用自动加载 dotenv。
