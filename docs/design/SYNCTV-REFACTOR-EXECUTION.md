## 必须守住的边界

- 共享播放器本身不是需要废弃的对象；需要移出的是散落在个人播放器和全局会话中的旧房间业务规则。
- 不能只将 Socket.IO 地址换成 SyncTV 地址。隔离实验已确认旧握手及本站旧来源格式不直接兼容。
- 房间成员关系、观看模式、当前页面、播放控制权和画面形态是不同状态；个人音量、字幕外观和弹幕显示不应被误当成房间播放进度。
- SyncTV 的来源、清晰度和倍速同步行为，以及客户端误差校正也要接入，不能只换服务端后沿用旧同步规则。
- 新旧房间不得同时向同一播放会话发布控制。切换前明确唯一控制来源，验收后清理旧桥。

## 2026-11-11 实际验证

重建隔离环境后 SyncTV v1.0.14 和 PostgreSQL 18.6 成功启动。首次启动中的 PostgreSQL 段错误在新隔离库中未复现，根因仍未知，不能称已修复根因。测试脚本复制到新目录后，原来的相对媒体路径失效；补齐测试媒体位置并使用独立测试名称后，协议检查 28 项通过，数据库及服务重启后的检查 5 项通过。首次脚本执行因媒体缺失失败，因此外围启动脚本最终退出 1；应分别阅读后续两份实际检查结果，不将其包装成整个启动脚本通过。

早期浏览器检查只到房间目录。后续已在两个独立持久化 Chrome 会话中，以房主和普通成员实际播放同一段 90 秒动态 MP4，验证暂停、跳转、恢复、刷新重新入房及聊天到达；详见下节。本站真实账号、真实来源、本地封面上传及迁移尚未接通。

## Chrome 实际播放验收补充

用户亲自完成协议确认后，测试使用两个独立 Chrome 持久化浏览器配置目录，分别登录 `codex_test_root` 与 `codex_browser_member`；视口均为 1440×900。使用本地生成的 90 秒动态视频及测试音轨，媒体服务支持 HTTP Range，并创建独立媒体记录以排除替换原两秒片源后的缓存和旧状态。

实际视频元素观测及独立断言通过：

- 两端视频都处于播放状态，间隔约 2.5 秒采样，视频时间均推进超过 2 秒。
- 房主暂停后，两端视频均暂停，采样进度差约 0.051 秒。
- 房主跳转后，两端均到达 34.832 秒，保持暂停；恢复后两端继续播放。
- 成员刷新页面、重新进入房间后，两端继续实际播放，采样进度差约 0.064 秒。
- 房主通过界面发送测试聊天，第二端界面显示同一消息，并显示聊天弹幕。

这些是单机回环、顺序采样的测试结果，不是同步误差 SLA，也不是跨公网、手机或弱网的验收。已观测视频解码、时间推进及非静音状态；没有人工听音或音频回路采样，不能宣称真实扬声器声音已验收。

此前“进度变化但画面停首帧”未被证明为上游产品缺陷：Chrome 自动化明确记录 Flutter 无障碍覆盖层拦截播放按钮点按，改用默认画面上的原生鼠标操作后完成实播。内置浏览器现象的完整根因未独立定位，不再将其作为 SyncTV 播放失败的结论。
